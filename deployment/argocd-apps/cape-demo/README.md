# cape-demo

The CAPE demonstrator stack: the Ryax workflow engine plus the demo workloads that run
on it.

| subfolder | what it is |
| --- | --- |
| `ryax/` | The Ryax workflow-automation engine — the platform the demos run on. |
| `ipto-scada-anomaly-detector/` | PostgreSQL for the IPTO SCADA anomaly-detection Ryax workflow. |

## Naming

Each subfolder gets its own ArgoCD Application, in a file named
`deployment/argocd-apps/app-of-apps/cape-demo-<subfolder>.yaml`.

⚠ That is the FILENAME. The Application **name** inside `cape-demo-ryax.yaml` is still
plain `ryax`, deliberately. ArgoCD keys resource tracking on the Application name
(`argocd.argoproj.io/tracking-id: ryax:/…`), not on the filename or the source path, so
renaming the Application would orphan every live resource and — with `prune: true` —
delete and recreate them, the 100Gi nix store and 60Gi registry PVC included. The
filename is free to change because `apps-root` renders every file in that directory
regardless of what it is called; the name inside is not.

## Nothing here is backed up

Every volume in this stack is excluded from Longhorn's recurring snapshot and S3
backup jobs. What these workloads store is re-importable rather than authored in
place: build caches, action images, execution artifacts, observability retention
windows, and demo data that is regenerated by re-running a workflow. The workflows
themselves are owned by their authors and imported through the Ryax UI.

Policy: [ryax/snapshot-policy.yaml](ryax/snapshot-policy.yaml), a PostSync hook that
re-applies the exclusion on every sync so it survives a cluster recreate. It covers
both `ryaxns` (the engine) and `ryaxns-tools` (the demo databases).

⚠ One hook covers both namespaces, so it belongs to the **ryax** app but enforces the
other apps' storage policy too. Deliberate — a second near-identical copy would drift —
but it means disabling ryax stops the policy being re-applied to the demo databases as
well. Add new namespaces to `PVC_NAMESPACES` there rather than copying the hook.

⚠ Consequence, accepted: these volumes have no off-site copy and no point-in-time
history. If something here ever holds state worth keeping, take a one-off manual
backup rather than re-enabling the daily job for the whole namespace.
