# eda-hyperlynx-2604 — Siemens HyperLynx 2604 as a CONTAINER module

Build-only. This app owns the machinery to build and publish the runnable HyperLynx module
image (`deployments/infrastructure/eda/modules/hyperlynx:2604`):

- `namespace.yaml` — one namespace per EDA app, named after it
- `postsync-build-image.yaml` — the build trigger (mirror build files → GitLab → pipeline
  on the `[eda]` runner)
- `postsync-register-module.yaml` — re-registers the module after a cluster recreate
- `build-files-configmap.yaml` — Dockerfile + `.gitlab-ci.yml` + `module.yaml`, mirrored

Its Application is generated by `app-of-apps/eda-modules-appset.yaml`, not by a file of
its own.

**No secrets of its own.** The installer media is on the TrueNAS artifacts export and the
registry push credential is sealed by `image-registry` (which `sealAllSecrets.sh` runs).

## How it runs

HyperLynx runs **inside the shared remote-desktop pod**: a user runs `module load
hyperlynx/2604` and the desktop's podman runs this image. There is no
desktop/Guacamole/VNC here.

⚠ **Building the image does NOT make it loadable.** The module must also be REGISTERED in
the module registry, which is the broker's authority for what may run:

```
deployment/argocd-apps/remote-desktop/register-module.sh add hyperlynx 2604
```

Registration is automatic on a recreate via the PostSync Job above; this is for ad-hoc work.

## Media path asymmetry

⚠ This module's media path uses the **MODULE** name as its first segment
(`hyperlynx/2604`), while the two xilinx apps use a **VENDOR** name (`xilinx/2024.1`). That
is a real inconsistency and it is **deliberate**: the segment is an arbitrary string whose
only requirement is that this app's CI and `eda/fileserver`'s `SUBDIRS` derive the SAME one.
Do not "fix" either side for symmetry — `eda/fileserver/check-subdirs.sh` asserts they agree.

⚠ It also builds `FROM quay.io/centos/centos:stream9` rather than ubi9, because ubi9's repos
are a subset of RHEL's and lack `xorg-x11-server-Xvfb`.
