# eda-petalinux-2024-1 — PetaLinux 2024.1 as a CONTAINER module

Build-only. This app owns the machinery to build and publish the runnable PetaLinux 2024.1
module image (`deployments/infrastructure/eda/modules/petalinux-2024-1:2024.1`):

- `namespace.yaml` — one namespace per EDA app, named after it
- `postsync-build-image.yaml` — the build trigger (mirror build files → GitLab → pipeline
  on the `[eda]` runner)
- `postsync-register-module.yaml` — re-registers the module after a cluster recreate
- `build-files-configmap.yaml` — Dockerfile + `.gitlab-ci.yml` + `module.yaml`, mirrored
  into GitLab

Its Application is generated by `app-of-apps/eda-modules-appset.yaml`, not by a file of
its own.

## Naming: `petalinux/2024.1`, never `petalinux-2024.1`

The user-facing form is `module load petalinux/2024.1` — `<name>/<version>`, exactly like
`xilinx/2024.1`. The DASHED spelling `petalinux-2024-1` appears only where a dot or a slash
is illegal: this directory, the k8s namespace, the GitLab project and the image repository.
`module.yaml` carries the two halves separately (`name: petalinux`, `version: "2024.1"`) and
everything else is derived from them.

## How it runs

PetaLinux runs **inside the shared remote-desktop pod**: a user runs `module load
petalinux/2024.1` and the desktop's podman runs this image. There is no
desktop/Guacamole/VNC here.

⚠ **Building the image does NOT make it loadable.** The module must also be REGISTERED in
the module registry, which is the broker's authority for what may run. This module
publishes to a NON-DEFAULT repo (`module.yaml`'s `image:` key), so the manifest must be
passed explicitly:

```
deployment/argocd-apps/remote-desktop/register-module.sh add petalinux 2024.1 \
  deployment/argocd-apps/eda/petalinux-2024-1/module.yaml
```

Registration is automatic on a recreate via the PostSync Job above; this is for ad-hoc work.

## What a user gets, and what they do not

`module load petalinux/2024.1` puts the eight `petalinux-*` tools on PATH as wrappers. Each
runs the image with `$HOME` bind-mounted and the caller's own uid, and the shim inside the
image sources `/opt/petalinux/settings.sh` first — there is nothing to source by hand.

⚠ **No TTY, so no menuconfig.** The launcher protocol has no stdin: it writes a run request
and streams the container's log back. A bare `petalinux-config` (which opens menuconfig) has
nothing to draw on. Use the non-interactive forms:

```
petalinux-create -t project --template zynqMP -n myproj
cd myproj
petalinux-config --get-hw-description /path/to/system.xsa --silentconfig
petalinux-build
```

**Installed platforms: all four — `arm aarch64 aarch64_dt microblaze`.** That is Zynq-7000
(`arm`) and Zynq UltraScale+/Versal (`aarch64`) through the classic `.xsa` handoff, the same
UltraScale+/Versal parts through the **System Device Tree** flow (`aarch64_dt`, whose
hardware handoff is an SDT from Vivado/Vitis `sdtgen`), and MicroBlaze soft cores.

A project picks its flow at creation, and one built for a flow that is not installed fails
on missing sources — which is why nothing is left out. It is affordable: a platform is a set
of Yocto recipe layers costing ~17 MB, not a toolchain (see the size table below).

⚠ **`petalinux-boot --jtag` cannot reach a board from here.** It needs `hw_server` and USB
access to a cable; this container has neither, and the Vivado module is a *different*
container. Program hardware from a machine with the cable attached.

⚠ **BitBake builds land in `$HOME`, which is NFS.** That is the only writable path the
launcher mounts. Yocto on NFS is slow and, with two builds of the same project at once, can
corrupt its own locks — keep one build per project directory. If build throughput becomes
the complaint, the fix is a node-local scratch mount in `module-podman.sh`, which affects
every module and is therefore a remote-desktop change, not a change here.

PetaLinux needs **no license server** — `module.yaml` has no `env:` block, unlike the Xilinx
and HyperLynx modules.

## Installer media

One file, named in full by `$MEDIA_RUN` in `.gitlab-ci.yml`:

```
/artifacts/xilinx/petalinux-v2024.1-05202009-installer.run
```

i.e. `\\fs-1.ad.base.internal\eda\xilinx\` from a workstation — the same flat directory the
two Vivado SDI tarballs live in. The pipeline copies **only that file** onto node-local
`/build-scratch/petalinux-2024-1-media` (it must be executable, and the export is shared),
and buildah bind-mounts that directory build-time only.

## Build cost

First green pipeline, 2026-09-04 on ecc197: **~8 minutes** pod start to pushed — 2m00s for
the installer itself, 1m58s for the push, the rest apt and assertions. A re-run skips the
media staging (marker on `/build-scratch`).

⚠ Do not copy the Vivado apps' 3–6 h budgets here. There is no Xvfb, no `xsetup` and no
115 GB of media; this app's `timeout: 4h` is pure headroom for a slow push.

## Where the disk goes

Measured 2026-09-04 with `--platform "arm aarch64 aarch64_dt"`:

| path | size | what it is |
| --- | --- | --- |
| `/opt/petalinux` | **11 GB** | the whole install |
| `components/xsct` | 9.8 GB | Xilinx SCT — the hardware-handoff tooling (XSA/SDT parsing, device-tree generation, `xsdb`). **89% of the image** |
| `sysroots/x86_64-petalinux-linux` | 649 MB | the host sysroot the tools themselves run out of |
| `licenses` | 244 MB | license texts |
| `components/yocto` | 50 MB | the platform source sets — **17 MB each**, measured for arm, aarch64 and aarch64_dt |
| `scripts`, `templates` | ~1 MB | project templates and helper scripts |

⚠ **`--platform` is not the disk lever it looks like.** The per-platform content is
`components/yocto`, at 17 MB per platform — the entries select *recipe layers*, not prebuilt
toolchains. That measurement is why `microblaze` was added rather than argued about, and why
dropping one would save nothing worth having. The 9.8 GB is XSCT, and every platform shares
it.

⚠ **This is the INSTALL size, not what a build needs.** `petalinux-build` fetches sources
and sstate into the project directory in `$HOME` — tens of GB per project, on the NFS home.
That, not the image, is what fills up.

The build re-prints this breakdown between its `==== INSTALLED SIZE` markers on every run,
so it stays honest across releases.

## What the first builds taught, in order

Every one of these was found by a failing pipeline, and each is now a comment in the file
it belongs to. Listed because the same traps apply to a future PetaLinux version:

1. `tftpd` (on UG1144's list) cannot be installed in a container — its postinst wants an
   inetd superserver and dpkg exits 1, failing the whole apt step.
2. `--platform` is **space**-separated. A comma is read as one unknown platform name.
3. The installer has `-y` ("automatic yes to all prompts"); no stdin feed is needed.
4. `less` and `lsb-release` must be named explicitly under `--no-install-recommends`. A
   missing `lsb_release` also fakes a `[WARNING] This is not a supported OS`, because the
   OS check greps that binary's output.
5. Every tool is a python3 argparse script, and argparse's HelpFormatter calls
   `shutil.get_terminal_size()`, which **segfaults** in this sandbox — all eight tools
   exited 139 with no output until `COLUMNS` and `LINES` were set (both, positive).
6. Sourcing `settings.sh` from the shim passed the CALLER's arguments to it, and it reads
   `$1` as the install directory — so `petalinux-util --version` made `$PETALINUX` the text
   of `readlink --version`.
7. 2024.1 has **no `tools/` directory** — the path older releases keep the `petalinux-*`
   binaries in does not exist. Both the shim and the build-time assertion locate the tools
   instead of assuming a path.

The failure path that dumps the installer's own `--help` and log tail is what produced 2,
3 and 4. Keep it: the media is only reachable from the `[eda]` runner, so a build log is
the only place its usage text can be read.
